На собесе я бы строил ответ вокруг идеи: неважно, кто написал код — джун, сеньор или AI-агент. Качество определяется не автором, а тем, насколько код удовлетворяет требованиям и насколько мы умеем это проверить.

Что такое качественный код? Я бы разделил качество на несколько измерений:

* Correctness — код делает то, что должен, включая edge cases.
* Reliability — нормально ведёт себя при ошибках, таймаутах, частичных отказах, повторных запросах.
* Maintainability — его можно понять, изменить и расширить без переписывания половины системы.
* Simplicity — нет ненужной сложности и overengineering.
* Performance — удовлетворяет требованиям по latency, CPU, memory, throughput.
* Security — нет очевидных уязвимостей, утечек секретов, неправильной валидации.
* Consistency — соответствует архитектуре, стилю и conventions проекта.
* Observability — проблемы можно обнаружить: logs, metrics, tracing.

При этом главный момент для AI: нельзя оценивать качество по тому, насколько убедительно выглядит код. Нужны проверяемые критерии.

Я бы представлял это как pipeline:

Requirements → implementation → static checks → tests → review → deployment → runtime monitoring

И здесь уже появляются технические средства.

Во-первых, статические проверки. Для Go это, например:
```shell
gofmt / gofmt check
go vet
staticcheck
golangci-lint
```

Плюс dependency/security scanners вроде govulncheck, SAST, secret scanners. Они ловят целые классы проблем ещё до запуска программы.

Во-вторых, автоматические тесты:

```
unit tests
integration tests
E2E tests
race tests
fuzz tests
benchmarks
```

Для Go особенно полезны:

```
go test ./...
go test -race ./...
go test -fuzz=...
go test -bench=...
```

Но важная фраза для собеса: наличие тестов само по себе не означает качество. Агент вполне способен написать код и тест, который подтверждает его же неправильное предположение.

Поэтому нужны проверки относительно внешней спецификации: API contract, acceptance criteria, expected invariants, integration tests, contract tests.

Например, если агент написал функцию перевода денег:

`A -> B, $100`

недостаточно проверить:

`transfer() returned nil`

Нужно проверить инвариант:

```
balance(A) decreased by 100
balance(B) increased by 100
total money didn't change
duplicate request didn't transfer money twice
failed transaction didn't partially change state
```

Вот это уже значительно сильнее проверяет correctness.

Третий уровень — code review. Причём review нужен не столько для проверки синтаксиса — это хорошо делают инструменты, — сколько для вопросов:

```
Почему решение устроено именно так?
Не нарушает ли оно архитектурные границы?
Что произойдёт при ошибке?
Какие assumptions сделал автор?
Не появилась ли ненужная сложность?
```

И здесь AI-код я бы рассматривал примерно как код от очень быстрого разработчика, которому нельзя полностью доверять его assumptions.

Четвёртый уровень — CI quality gates. Агент не должен иметь возможность просто сказать: «готово».

Например:
```
AI creates PR
      ↓
format/lint
      ↓
compile
      ↓
unit tests
      ↓
race detector
      ↓
integration tests
      ↓
security scan
      ↓
review
      ↓
merge
```

Если агент пропустил тесты — CI всё равно их запустит. Если код не компилируется — PR не merge’ится.

Это важный принцип: контроль качества должен находиться вне самого агента.

Ещё один слой — production verification. Даже идеально зелёный CI не гарантирует отсутствие проблем:

```
canary deployment
feature flags
metrics
logs
traces
error rate
latency
SLO / alerts
rollback
```

То есть качество проверяется не только до merge, но и после deployment.

И я бы в конце собеса сформулировал примерно так:

```
I wouldn’t judge code quality based on whether it was written by a junior, a senior engineer, or an AI agent.
I would define measurable requirements and build independent verification around them: static analysis, tests, CI quality gates, code review, security checks, and production monitoring.
```

The important part with AI agents is that the agent should not be the one deciding whether its own work is correct. The verification should be external and deterministic where possible.

И ещё одна хорошая мысль, если интервьюер пойдёт глубже:

`раньше bottleneck был написание кода. С агентами bottleneck постепенно смещается в specification и verification.`

То есть ценность инженера всё больше не только в:

`«умею написать 500 строк кода»`

а в:

`«умею точно определить, что должно быть сделано, и построить систему, которая доказывает, что результат достаточно хороший».`

Это, на мой взгляд, самый сильный концептуальный ответ на такой вопрос.
